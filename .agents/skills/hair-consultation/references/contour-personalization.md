# 先观察本人，再决定发型

在 Codex 内由多模态读图完成观察，再用本地编译器检查方案与输出提示词。编译器不识别人脸、不运行关键点模型、不调用图片模型；不能把其校验通过说成识别准确或生成效果合适。

## 观察输入

只依据本案例真实原照。正面看纵向/横向印象、颧侧到下颌的收窄趋势、下颌边缘、下巴轮廓、露额范围、发型外轮廓及眼镜与鬓角的视觉关系；侧照只补充其实际可见区域。保留原照ID、hash和实际查看记录。

每项写 `id`、`feature`、定性 `value`、可解释 `description`、`evidence_assets` 与 `confidence`（high/medium/low/unknown）。`vertical_impression` 可写 elongated/balanced/shorter/unknown，`hairline` 看不清必须 unknown。脸型名只能作为 tentative_photo_impression，可保留相邻类型；不用百分比、毫米、假精确三庭五眼、颜值分、骨骼诊断或人格推断。

模型任务：

```text
查看本案例真实原照，为发型设计记录可见的脸部轮廓和头发外轮廓。先检查照片质量、近距离透视、头部倾斜、光线、刘海和眼镜遮挡。每项观察写证据照片、把握程度和局限；看不清的内容保留unknown。不要根据AI基准反推真实脸型，不以模板空字段冒充分析结果。脸型只是可修改的视觉印象。
结合顾客原话确定审美目标；从轮廓观察推导头顶高度、两侧重量、刘海覆盖/走向、耳周和后颈的设计目标，解释理由。不要默认所有人都要鹅蛋脸，也不要把脸型标签当唯一推荐器。实际发质、发旋、烫染史、可用长度和打理意愿未知时保留未知或写条件。
输出符合contour-profile-template.json的已观察记录。把顾客主动要求、照片可见事实和设计推断分别写清。
```

## 设计计划

每款写 `id`、`name`、`family`、`geometry`（fringe/parting/sides/crown/perimeter）、`addresses_observations`、`personal_reason`、完整 `hair_spec`、`color`、`service_conditions`、`forehead_exposure` 和 `unknowns_to_check`。

标准12款至少覆盖4种真正不同的发型外轮廓。同一轮廓家族的款式至少在两个结构维度上有明确区别；换颜色、改名字不计为结构区别。结构编码使用稳定的可见类别，不用同义词换码逃过检查。圆盖感被拒绝时，应在前额走向、顶部轮廓、两侧堆积和耳周边缘上改变设计。

每款理由必须连到可见观察；未知发际线不能支撑“发际线完美所以后梳”的理由。露全额方案标明发际线待核对。明显剪短、留长、烫发或染浅写实施条件，设计探索不等于服务同意。

这些是审美设计启发，不是临床规则。纵向感明显时可优先控制额外顶部高度、保留适度侧边重量；顾客主动要高顶时记录有意取舍，不能强制按脸型排除喜欢的款式。轮廓判断不确定时优先使用明确可见特征与顾客偏好。

## 编译与生成

```sh
python3 scripts/compile_personalized_round.py /案例绝对路径 /轮廓记录.json /设计计划.json /新的输出目录
```

编译器核对原照与基准hash、依据链、轮廓家族和结构差异，输出每款完整提示词和本人设计说明。此时仍是planned_not_generated，实际调用计数为0。

有已授权生成要求时，再用内置图片工具逐款从同一基准分支，并引用真实正面照核对本人。改变头发来满足设计目标，不能改变脸、眼镜、年龄或肤色。保持既定的轻度基准整理，不逐款加美颜。

生成后另行查看：本人有没有变、结构是否实现、相邻款是否仍过分相近、轮廓是否比之前更清楚。计划通过检查不是图片通过。本人喜欢与理发师可行性也独立记录。仅咨询功能可行性或检查新逻辑时，先交付实际分析和可运行的设计计划，不自动新增一批图片调用。
