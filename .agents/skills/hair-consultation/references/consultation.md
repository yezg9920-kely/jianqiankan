# 顾客发型设计

把一次顾客咨询推进到可选的本人发型参考，再推进到顾客选定的方案。Codex 对话默认体验是“发真实照片 → 轮廓观察与审美目标 → 去原背景的高还原基准肖像 → 有个人依据的12张独立推荐 → 不喜欢就换方向 → 喜欢后细调”，不要求先填偏好表。工作台每轮的额度独立，按实际档位生图。用户指定数量或快速四格时按本次要求执行。主要交互是照片、大图、短说明和编号。

## 开始与续接

- 新顾客新建随机 case_id；一位顾客一个私有目录。已有案例先读 case.json，保留照片、历史结果与选择；不混用其他案例。
- 在当前可写项目的 private-workspace/hair-consultation/ 下保存案例；优先沿用用户已有的工作台案例目录或指定的目录；工作台接力见 [workbench.md](workbench.md)。
- 用 [assets/case-template.json](../assets/case-template.json) 建立记录。它是记录模板，不能把空字段当作已完成的照片检查、授权或审核。
- 必需：一张完整头顶、脸部清晰的真实正面照。侧面、背面只在顾客需要对应视图时补充，不阻塞正面初选。先查看本地照片。标准流程先以真实正面照编辑出干净浅色背景的本人基准肖像；侧照只作身份与头型核对，不平均出新脸。真实原照始终保留为身份依据，AI 基准不能冒充真实原图。
- 本工作流按用户已明确要求的“适当优化”处理基准：照片拍得不理想时，先自然整理曝光、白平衡、重阴影、临时皮肤瑕疵与取景留白，再推荐发型；顾客要求无修饰时遵守。优化强度以仍像本人为准，保留皮肤纹理、五官、真实脸型、年龄和辨识特征。美颜只在基准执行一次，不在不同发型里继续加重。不凭空修复无法看清的五官，不生成另一张模特脸。细则见 [photo-quality-and-layout.md](photo-quality-and-layout.md)。没有要求逐步确认时，助手目检后按已授权计划继续，基准仍记 pending_customer，不能伪造本人认可。明显变脸时先做有界修订。
- 使用本人照片或已获顾客授权的照片。已确认的授权在同一案例延续，不重复询问。用途不明确时，将“有权使用且同意交给当前云端工具做本次预览”合并确认一次；只影响生图，准备工作继续。
- 没给照片时，完成能做的准备，然后说明需要照片。不能擅自把旧案例照片、陌生人或合成人像当成本次顾客。

## 咨询与初选

1. 读取 [contour-personalization.md](contour-personalization.md)，先检查真实原照的可见范围、遮挡、透视与光线，记录定性的纵横印象、颧侧到下颌走势、下巴轮廓、现有头发外轮廓、眼镜与鬓角关系。每项带证据照片、hash、把握程度与局限，形成 contour_profile；不能用美颜基准倒推真实脸型。脸型名仅为可修正的照片印象，不做伪精确测量。发质、发旋、隐藏发际线与烫染史不清楚就记 unknown。
2. 先使用顾客已说过的发型方向与限制；未指定时，按照片呈现的外观、当前发型、可见发长和纹理，自动选择“男生发型 / 女生发型 / 中性发型”作为首轮设计方向，不先问“男生还是女生”。这是可随时修正的发型目录选择，不写成已确认的生理性别或性别身份。记录 preferences.style_direction 和来源 photo_style_inference；不能清楚选择时直接用中性方向，仍继续推荐。方向不强制发长，男生方向可以长发、女生方向也可以短发；顾客主动指定的方向优先。
3. 从已有对话提取希望长度、必须保留/避免、是否接受烫染漂、扎发和打理要求。顾客已要求发型与发色时，首轮就是完整搭配，必须安排可见的冷暖、明度和色调变化，不把“选剪裁后再看颜色”当作拖后已授权发色的理由；顾客只要剪裁或明确不染时保留原色。每套写清剪裁、发色和造型。剪短、留长、强卷、浅色等探索方案明确注明条件，不表示同意实际服务。明确的保长、不露额、不可烫染等限制优先。不因偏好未填而停下来提问，只有照片不可用、授权缺失或明确限制冲突时补问。
4. 标准批次规划12款独立图片，按已授权范围和当前工具容量分批，基准肖像不计入12款；用户明确要求“十张以上”不能用一张多格图或裁切冒充十张独立生成。先结合 contour_profile 与顾客审美原话形成设计目标，每款必须解释对应哪项可见特征，不能只凭脸型标签套模板。完整发型轮优先覆盖至少4种可见轮廓方向；同一方向各款至少在刘海、分线、两侧、顶部或外边缘中的两个结构维度上区分，换色不算新发型。依据用户本轮要求覆盖剪裁、分线、卷度和发色，明确实际几种剪裁与几种颜色。只比较发色时优先在同一款发型上分批做 12 款；明确要求同时比较两种剪裁时，可各做六色。优先读取 [xhs-library-guide.md](xhs-library-guide.md) 的实际参考库及其发色审计补充；通用结构见 [design-menu.md](design-menu.md)。不从外貌推断职业、性格或唯一最适合。
5. 在 case.json 写 options，每款记录 id、round_id、名称、结构、差异、个人依据、服务前提与待确认项。完整个性化设计轮可用 `scripts/compile_personalized_round.py` 检查轮廓依据、来源hash及结构差异并输出提示词；编译成功仍为planned_not_generated。当前批次用01–12等编号，并带轮次ID；旧A–D或旧版本不覆盖。无需让顾客批准整页参数。
6. 读取 [image-prompts.md](image-prompts.md)，使用真实可用的内置 image_gen。先生成一张基准，再对每款单独调用、始终从同一基准分支，同时引用真实原照核对本人，不把上一款继续改成下一款。统一干净背景、光线、衣服和画幅；基准完成后不逐款追加美颜。快速四格仅在用户选该模式时使用。最后可用代码把独立原件排成总览，但保留每张单独原件。
7. 目检本人特征、款式区分和约束，特别检查轮廓计划是否真正体现在图片上、是否仍统一成圆蓬模板。结构编码通过不表示生成图已通过。输出必须明确标“AI效果预览”；一张图含多个选项时分别记录可用/待修订编号。不能把“生成成功”记成顾客已认可。
8. 交付按 [photo-quality-and-layout.md](photo-quality-and-layout.md) 排版：编号与中文名称单列，人物和完整发型清晰可见，文字不压在脸上；提供总览、每页四款的大图及可放大的本地图册。电脑三列、手机单列，维持同组画幅、头部大小与基准优化一致。排版层不再次美颜。每款一条差异和一条打理条件，提示词放附属文件。最后用一句“选一个编号，或者告诉我换一组”收取反馈。此处等待是顾客选择，不能替顾客选择，也不能在等待期间擅自生成所有后续组合。

## 选择与微调

- 顾客说“都不喜欢 / 不合适 / 换一组”时，直接进入新一轮推荐，重新从同一真实原照分支生成；不再要求填一遍资料。已有具体反馈就优先落实；只有笼统否定时，主动更换刘海覆盖、分线或轮廓的结构家族，避开已拒绝款式，不把四个旧方案换名字重发。
- “太保守 / 更自然 / 不要露额 / 换女生发型 / 要中性一些”等反馈直接更新本案例条件；用户指定方向覆盖照片初步选择。不能为了让结果显得更男性化或女性化去改变脸部、年龄、肤色、妆容或服装。
- 每轮在 feedback_history 保存原话、对应 round_id、保留/排除项和下一轮调整；recommendation_round 只在真实开始一轮时递增。顾客没有回复时不自动刷图；明确要求换方案就是该轮继续生成的指令，在已授权调用额度内直接做。
- “B，刘海再短一点”表示选择 B 并指定微调；把原话与选项 ID 写 selection。若图片里某格与名称不符，按实际可见效果解释，不能照错标签继续。
- 同一款的细调可以比较两到三档刘海、长度、发色或纹理；一轮尽量只变一个维度。保留共同已接受母图，并同时引用真实原照核对本人。
- 发色、卷度沿用顾客已经表达的要求，不重复索取授权或强制先选剪裁。专门比色时可先选一款改动小的发型。原照发束凌乱时，轻理发流、刘海和两侧，保留整体长度与发际线；也可复用顾客或操作者确认的浅底成图。去除原照片背景，统一使用干净浅米灰底。固定每组剪裁、纹理、光线、肤色和美颜，分别从去过原背景的同一原发色母图分支；放大对照用对应剪裁的原发色母图，不能拿不同剪裁作颜色改善证据。“看看发色”只授权视觉探索，不表示同意实际染漂服务。明显剪短、留长、漂浅或额外造型需求写短条件说明。
- 对比图可以作为发型设计参考，最终单款仍从真实原照编辑，重述选中款完整结构；不要把整个四格图当唯一人脸参考。若需要从图中提取单格用于继续编辑，按当前图片工具的编辑能力操作，不用手写裁图替代发型编辑。
- 原照换了，先保留旧案例，再新建版本；旧输出不能自动配给新照片。每张最终图都能追到实际原照和选择。
- 没有真实对应角度照片，不把正面推生成的侧背图说成已知头型。仅顾客明确要求想象示意时另标“AI推测视图”。

## 执行与记录

- 遵循本次项目 AGENTS.md。当前默认仅 Codex 内置图片工具，不接付费 API、不索取 Key，不将订阅会话提供为公开服务；Mac／Windows 本地工作台使用用户已登录的官方 Codex CLI。
- 按用户明确数量制定有界调用计划。标准批次是一张基准加十二款独立方案，通常 13 次调用；失败与修订分别记录，先修主要问题，不无限重试。用户要求的新数量与美颜/背景方式优先于旧技能或项目默认；在案例中记录覆盖依据，不重复索取已明确的授权。未获授权不得静默改付费提供方或后台无界生成。
- 已授权且输入齐全就执行；不在每次调用前重复问是否继续。顾客选择、缺照片、缺授权和额度上限是不同等待原因。
- 缺工具记 blocked_tool_unavailable；缺照片记 blocked_missing_input。未真正调用工具不能写 running 或成功。读取当前工具 schema，按其要求传本地路径或最近图片，不猜不存在的参数。
- 每次调用保存实际完整 prompt、引用顺序/职责、输入和输出 hash、时间、结果路径与失败信息；不可见的模型名、token、费用填 null。保留旧版本，不覆盖失败样张。
- 生图后把需要持续使用的图片存入本案例 assets/；使用真实工具返回的文件或支持的导出路径，不假造下载成功。若只拿到可展示图片但无法落盘，说明此限制，不伪造本地资产记录。
- case.json 的 stage、runs、选择与视觉审核由操作者按真实事件更新。人工核对、本人确认、理发师可行性分别记，不用 AI 自评代替后两项。
- 不把原照或结果放 Git、公共 static、演示数据或默认日志。外发、公开展示、发给顾客仍按用户本次指令；不自动发送。

## 最终交付

首轮图册可用以下脚本，来源须为本案例已有的真实生成原件；脚本仅排版与制作预览缩略图，保留全部原件，不调用图片模型。先读排版细则，检查当前批次的统一裁剪是否保留所有发型边界；不能把本案例裁剪比例套给构图不同的顾客。

```sh
python3 scripts/render_lookbook.py /绝对路径/已有批次 /绝对路径/新的排版版本
```

顾客确定后保留单款大图和简短理发沟通要点：刘海、两侧、顶部、耳周、后颈、保留/避免、打理、所需服务与待理发师确认项。没有实际报价不填数字；没有确认的厘米数、染发配方不编造。

需要沟通卡时读取 [case-record.md](case-record.md)，使用：

```sh
python3 scripts/render_card.py /绝对路径/案例/case.json
```

脚本只排版原照和已选定的单款文件，不重新生成人像。只有顾客确认本人、视觉审核通过且来源 hash 匹配的结果可以进入卡片。没有理发师意见时仍显示“待理发师确认”。

本阶段验收：有可选图、有真实选择记录、有选定结果；身份未确认或未实测就保留该状态。Mac／Windows 工作台与对话默认各自读本地文件，按 [workbench.md](workbench.md) 配置共享案例目录。
